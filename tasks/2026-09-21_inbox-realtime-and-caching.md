# Inbox: миттєве оновлення (SSE), плавний рендеринг, кеш медіа, дрібна стабільність

## Статус
done

## Задача
`/inbox` мав відчуватись швидше й стабільніше — ближче до Telegram Desktop:
миттєва доставка повідомлень замість очікування наступного полінгу, без
"мигання" списку розмов при кожному оновленні, швидке повторне відкриття
вже переглянутих медіа, і кілька дешевих правок стабільності з попереднього
архітектурного ревʼю. CRM-звʼязок (`Conversation.client_id`) свідомо не
чіпали — окрема задача.

## План
- [x] Push замість очікування полінгу: Redis pub/sub + SSE-ендпоінт `/inbox/stream`
- [x] gunicorn на `gevent`-воркерах, щоб довге SSE-зʼєднання не займало весь воркер
- [x] Diff-рендеринг списку розмов замість повного `innerHTML`-ребілду
- [x] Оптимістичне відправлення (бабл зʼявляється миттєво, до відповіді сервера)
- [x] `Cache-Control`/ETag на `/inbox/media/<id>/<idx>` (файли незмінні — uuid-імена)
- [x] Індекс `messaging_message(conversation_id, external_message_id)` — дедуп/edit/delete запити
- [x] Обмежений `ThreadPoolExecutor` замість необмежених `threading.Thread` для префетчу медіа
- [x] `/inbox` фільтрує канали доступу в SQL (`WHERE id IN (...)`), а не в Python
- [ ] ~~Звести дві admin-перевірки (`user_type` / `has_role`) в одну~~ — перевірив: це не дрейф,
  а свідомий репо-вайд патерн (той самий дубль є в `activity_log/routes.py:41`,
  `notifications/routes.py:21`), обидва поля виставляються разом при створенні юзера
  (`settings/routes.py:827-830`). Консолідація лише тут внесла б непослідовність із рештою
  кодбази — свідомо не чіпали.

## Реалізація
- `app/services/messaging/events.py` (новий) — `publish(event_type, channel_id, conversation_id)`,
  Redis pub/sub на канал `inbox:events`. Best-effort — усі винятки логуються, ніколи не піднімаються.
- `app/services/messaging/inbox_service.py`:
  - `events.publish(...)` викликається після кожного commit'у, що реально змінює стан треда:
    нове вхідне повідомлення, edited, deleted, і `send_reply` (вихідне).
  - `_MEDIA_POOL = ThreadPoolExecutor(max_workers=4)` — `prefetch_message_media` тепер
    `.submit()` в пул замість `threading.Thread(...).start()` без обмежень.
- `app/blueprints/inbox/routes.py`:
  - `GET /inbox/stream` — SSE-ендпоінт. Підписується на Redis-канал `inbox:events`,
    фільтрує події по `accessible_channel_ids(current_user)` (перевіряється один раз при
    відкритті зʼєднання — довге зʼєднання не підхопить новий доступ без перепідключення,
    прийнятно для менеджерського use-case), шле `data: {...}` рядки. Порожні `: ping`-коментарі
    кожні 15с для keep-alive (не тригерять `EventSource.onmessage`).
  - `/inbox/media/<id>/<idx>` — `send_from_directory(..., max_age=2592000, conditional=True)`.
- `app/models/message.py` — `db.Index('ix_messaging_message_conv_extmsg', 'conversation_id', 'external_message_id')`
  в `__table_args__`.
- `migrations/versions/add_messaging_message_indexes.py` — новий, `down_revision='add_whatsapp_channel'`
  (актуальний head на момент задачі, перевірено скриптом, а не візуально).
- `entrypoint.sh` — `gunicorn --worker-class gevent --worker-connections 250` замість
  дефолтних sync-воркерів. Без цього SSE-зʼєднання від кожної відкритої вкладки менеджера
  займало б увесь sync-воркер на весь час сесії — з 4 воркерами це швидко вичерпало б ємність.
  **Compromise, свідомо не робили**: без psycogreen-патчу для psycopg2, блокуючий SQL-запит
  всередині greenlet все одно притримає інші greenlet'и цього воркера на час запиту (зазвичай
  одиниці мс) — прийнятно для обсягу цього CRM, але якщо навантаження суттєво зросте, варто
  повернутись і додати psycogreen або перейти на async-стек.
- `requirements.txt` — додано `gevent`.
- `app/static/js/inbox.js`:
  - `connectStream()` — `EventSource('/inbox/stream')`, на кожен `onmessage` дебаунсить (200мс)
    `pollList()` і, якщо подія стосується відкритого треда, `fetchThread(false)`. Полінг
    (10с/30с список, 5с тред) лишився як є — SSE лише прискорює, не замінює, тож розсинхрон
    при обриві зʼєднання неможливий (EventSource сам перепідключається).
  - `renderList()` — тепер патчить існуючі `.conv`-вузли по `data-id` замість повного
    `innerHTML`-ребілду: без миготіння, без повторного біндингу click-хендлерів щопулінг.
  - Оптимістична відправка: `appendOptimistic()`/`removeOptimistic()`/`markOptimisticFailed()`
    у `inbox.js`. Бабл із статусом `pending` (приглушений, іконка-годинник) додається одразу
    при сабміті, прибирається коли приходить реальна відповідь сервера (`removeOptimistic`),
    або позначається `failed` при мережевій помилці.
  - `appendMsgs()` тепер дедупить по `data-mid="<id>"` — потрібно, бо SSE-триггерений
    `fetchThread` і власна відповідь на `reply` можуть обидва принести те саме повідомлення;
    хто прийшов першим — рендерить, другий — лише оновлює курсори пагінації.
  - `msgNode()` — новий стан `pending` (клас + іконка-годинник), і рендер `media.type==='uploading'`
    (заглушка "файл завантажується" для оптимістичного бабла з вкладенням).
- `app/templates/inbox/index.html` — `.msg.pending .msg__bubble { opacity: 0.6; }`.

## Як тестувати
1. `docker compose up --build` (потрібен перезбір образу через новий `gevent` в requirements
   і зміну `entrypoint.sh`).
2. Відкрити `/inbox` у двох вкладках/браузерах під різними менеджерами з доступом до одного
   каналу. Надіслати повідомлення в один канал (напр. написати боту в Telegram) — очікується,
   що воно з'явиться в списку розмов **майже миттєво** (не через 10с), без миготіння всього списку.
3. Відповісти з CRM — бабл має з'явитись одразу (приглушений, з годинником), і за секунди
   переключитись на звичайний вигляд з "check"-галочкою.
4. Вимкнути мережу на кілька секунд під час відправлення (DevTools → offline) — бабл має
   позначитись як `failed` (червоний), без дублювання при відновленні мережі.
5. Відкрити вкладення (фото) двічі — другий раз має завантажитись миттєво з кешу браузера
   (Network tab → `304` або `(from disk cache)`).
6. `flask db upgrade` — переконатись, що нова міграція `add_messaging_message_indexes`
   застосовується без конфлікту heads.

## Edge cases
- SSE-зʼєднання обірвалось (перезапуск контейнера, мережева проблема) — `EventSource`
  перепідключається сам; існуючий полінг тим часом продовжує працювати як і раніше, тож
  функціональних регресій немає, лише тимчасово зникає "миттєвість".
- Redis недоступний — `events.publish()` ковтає виняток і логує; ingest/send не ламаються.
  SSE-ендпоінт у такому разі просто ніколи не пришле подій (де-факто деградує до чистого полінгу).
- Дві вкладки одного менеджера відкриті одночасно — кожна тримає власне SSE-зʼєднання
  (усередині `worker-connections 250` на воркер — з запасом для малої команди).
- Менеджеру видали доступ до нового каналу, поки в нього вже відкрита вкладка `/inbox` —
  список доступних `channel_id` для SSE-фільтра рахується один раз при відкритті `/inbox/stream`;
  новий канал підхопиться тільки після перезавантаження сторінки (як і раніше було з рештою UI,
  що теж читає доступ при заході на `/inbox`).
