# One-click деплой на стейджинг ВПС (Hetzner)

## Статус
done

## Задача
Пользователь арендует временный ВПС на Hetzner для тестирования
`feature/messaging-service` перед прод-деплоем, и хочет деплоить туда
через GitHub Actions "одной кнопкой" — так же, как прод-деплой, — чтобы
можно было арендовать/удалять стейдж-ВПС по мере необходимости (платить
только за дни использования) без переписывания workflow каждый раз.

## Реализация
Существующий `.github/workflows/deploy-dev.yml` уже был почти тем, что
нужно (SSH-деплой на отдельный dev-сервер, отдельные секреты
`DEV_SERVER_*`), но:
- деплоил "что бы ни было руками зачекаучено" через голый `git pull`
  без явного указания ветки/тега — не самодостаточно, легко забыть
  на каком ref сервер;
- health-check был одноразовым `sleep 6` + один curl — не ждал, если
  контейнер поднимался чуть дольше;
- Telegram-уведомление показывало `${{ steps.version.outputs.tag }}`,
  который никогда не использовался в самом деплое (deploy-dev вообще не
  чекаутил тег) — вводящая в заблуждение надпись;
- захардкожен чужой IP (`34.162.233.78`) и путь
  (`/home/bilobrov_vladyslav/apps/crmKvitkovaPovnya`) от предыдущего сервера.

Изменения в `deploy-dev.yml`:
- `workflow_dispatch.inputs.ref` — какую ветку/тег деплоить, дефолт
  `feature/messaging-service`. Значит кнопка "Run workflow" в GitHub UI
  сразу предлагает это поле, можно передеплоить другую ветку без правки
  файла.
- Убран лишний `actions/checkout` + шаг "Get latest tag" на раннере —
  они ничего не давали, весь чекаут происходит на самом ВПС по SSH.
- SSH-скрипт теперь явный: `git fetch origin && git checkout "$DEPLOY_REF"
  && git pull origin "$DEPLOY_REF"` — сервер всегда синхронизируется с
  тем ref, что указали в кнопке, а не с тем, что там оказалось зачекаучено
  руками в прошлый раз.
- Health-check — цикл до 15 попыток по 2с (`curl -sf .../auth/login`)
  вместо одного `sleep 6` — переживает чуть более долгий холодный старт
  (миграции + gevent-воркеры). При провале печатает
  `docker compose logs --tail=80 web` прямо в лог экшена — не надо лезть
  по SSH разбираться, что упало.
- Telegram-уведомления показывают реальный задеплоенный ref и адрес
  сервера (`${{ secrets.DEV_SERVER_HOST }}`), без старого чужого IP.
- Путь на сервере — `/opt/crm` (нейтральный, не завязан на чьё-то домашнее
  имя пользователя) — см. чеклист ниже, куда клонировать репо на новом ВПС.

## Разовая настройка нового Hetzner ВПС (сделать один раз, не автоматизировано)
1. Поднять ВПС, поставить Docker + Docker Compose.
2. Сгенерировать SSH-ключ для GitHub Actions:
   `ssh-keygen -t ed25519 -f deploy_key -N ''` — публичный ключ добавить
   в `~/.ssh/authorized_keys` на ВПС, приватный — в секрет GitHub
   `DEV_SERVER_SSH_KEY`.
3. Секреты репозитория (Settings → Secrets → Actions):
   `DEV_SERVER_HOST` (IP нового ВПС), `DEV_SERVER_USER`,
   `DEV_SERVER_SSH_KEY` — `TG_BOT_TOKEN`/`TG_CHAT_ID` уже есть (общие с
   прод-деплоем).
4. На ВПС: `git clone <repo-url> /opt/crm && cd /opt/crm && git checkout
   feature/messaging-service`.
5. Создать `/opt/crm/.env` — **отдельная, пустая БД для стейджа**, не
   копия прод-дампа (это одноразовый публичный тестовый сервер — не
   стоит держать там реальные данные клиентов дольше, чем нужно для
   теста). Обязательно: `SECRET_KEY`, `DATABASE_URL`/`POSTGRES_*`,
   `REDIS_URL`, свежесгенерированный `MESSAGING_SESSION_KEY`
   (`python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`),
   `ADMIN_USERNAME`/`ADMIN_PASSWORD` (создаст первого админа через
   `flask ensure-admin` в entrypoint.sh). Остальные `INBOX_*`-токены —
   по желанию, без них просто соответствующий канал не подключится.
6. Один раз руками: `docker compose up -d --build` — поднимет БД,
   прогонит миграции, создаст админа.
7. Дальше — GitHub → Actions → "Deploy to Dev" → Run workflow (можно
   поменять `ref`, если понадобится задеплоить что-то другое) — и это
   уже та самая "одна кнопка".

## Как тестировать
`python3 -c "import yaml; yaml.safe_load(open('.github/workflows/deploy-dev.yml'))"`
— YAML валиден (запускал, ок). Сам workflow не запускался «в бою» — ВПС
ещё не существует; первый реальный прогон будет самой проверкой.

## Edge cases
- Секреты `DEV_SERVER_*` из прошлого использования (если были нацелены
  на старый/уже не существующий сервер) — перед первым запуском
  обязательно обновить значения на новый Hetzner ВПС, иначе SSH-шаг
  просто не подключится.
- `git pull origin "$DEPLOY_REF" || true` — если когда-нибудь деплоят
  тег, а не ветку, `git checkout <tag>` уводит в detached HEAD, и
  `git pull` там бессмысленен/может выдать ошибку — специально
  проглатывается (`|| true`), чекаут тега сам по себе уже на нужном
  коммите.
- Этот workflow никак не связан с прод-`deploy.yml` — деплои друг на
  друга не влияют, разные секреты/сервера.
